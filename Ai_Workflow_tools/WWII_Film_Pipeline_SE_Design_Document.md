## 1. Guiding Principles

These principles govern every design decision below and should be checked against any future addition to the pipeline.

1. **100% local execution.** No cloud-dependent tools in the production path. Any tool under consideration must first pass a "does this run without a network connection" check before capability is evaluated.
2. **Scenes/shots request assets — they never create them directly.** All 3D, 2D, and audio assets are produced once, versioned, and reused. This prevents asset-explosion and continuity drift.
3. **AI proposes, humans approve.** Every stage that touches historical fact, creative interpretation, or emotional tone has an explicit human approval gate. Automation handles mechanical/repetitive work; humans own Tier 3 (pacing, framing, emotional truth, historical sensitivity).
4. **Evidence hierarchy over invented canon.** Nothing the system doesn't know is silently guessed into a fact. Unknowns are tracked as open wish-list items (`BLOCKER` / `NON-BLOCKER`), not filled in invisibly.
5. **Quality effort scales to camera proximity and story weight, not perceived "importance."** Hero/Primary/Secondary/Crowd/Distant tiers apply to every asset class — characters, costumes, environments, vehicles, voices.
6. **Layered variation, not duplication.** Base asset + condition/weather/damage/period layers, rather than full duplicate assets per variant.
7. **Craft over automation at the emotional core.** The most technically automatable scenes (crowd/context/background) get the most automation. The scenes the whole film exists for (Hiroshi's reckoning, Reia's arc turns) get the least — human-directed pacing, performance, and restraint.

## 2. System Architecture — Overview

```
Subsystem A: Narrative Intelligence
   Novel → extraction passes → evidence database → wish list →
   screenplay → scene breakdown sheets

Subsystem B: Asset Construction Pipeline
   Approved breakdowns → requirement aggregation → reuse/build routing →
   specification → construction → validation gates → asset library

Subsystem C: Character & Performance Pipeline
   Character bible → DAZ/Genesis base+age variants → rigging →
   local mocap → cloth sim → identity/costume/regime LoRAs →
   base voice model → age-derived voice variants

Subsystem D: Render & Style Pipeline
   Blender guide passes (depth/lineart/flat-color/material-ID) →
   directorial camera/lighting presets → ComfyUI stylization
   (six aesthetic regimes) → styled shot output

Subsystem E: Compositing & Assembly
   Styled passes → per-shot composite (Blender/Natron) →
   Resolve auto-populated timeline → director pacing pass →
   color grade → final scene/film output

Production Management Layer (Kitsu + MongoDB)
   Task tracking, approval gates, automated/manual scene modes,
   asset/scene lineage, provenance
```

Each subsystem is decoupled — different hardware profiles, different times of use, connected only through the shared production database.

## 3. Subsystem A — Narrative Intelligence

**Purpose:** Convert prose into a source-grounded, structured production record. The novel is treated as a RAG corpus, not summarized from model memory.

### 3.1 Evidence Hierarchy

Every extracted fact carries a status:

```
EXPLICIT    — directly stated in the novel/approved historical source
DERIVED     — calculated from explicit facts
INFERRED    — strongly suggested, not stated
PROPOSED    — generated by the system to fill a production need
APPROVED    — reviewed and accepted as canon
REJECTED    — reviewed and disallowed
UNKNOWN     — required, not yet established
CONFLICTED  — sources disagree
```

Nothing moves from `PROPOSED` to `APPROVED` without a human decision.

### 3.2 Ten-Pass Extraction Pipeline

```
Pass 1: Narrative extraction
Pass 2: Timeline construction
Pass 3: Character and relationship extraction
Pass 4: Location and asset extraction
Pass 5: Conflict and contradiction detection
Pass 6: Scene boundary proposal
Pass 7: Adaptation outline
Pass 8: Screenplay draft
Pass 9: Breakdown-sheet generation
Pass 10: Validation against source and canon
```

Recommended build order: prove Pass 1 against one real chapter before finalizing the full schema.

### 3.3 Three Screenplay-Level Outputs

1. **Shooting script** — scene headings, action, dialogue, source references, explicit tags distinguishing narrative fact / adaptation choice / historical insertion / visual interpretation.
2. **Scene breakdown sheet** — cast, extras, props, wardrobe, set dressing, effects, mocap/facial requirements, historical references, style profile, source passages, approval status.
3. **Continuity and provenance report** — why the system believes each fact and where it came from.

### 3.4 Identifier Hierarchy

```
Narrative Segment ID → Screenplay Scene ID(s) → Shot ID(s)
```

Every rendered frame traces back through this chain to the novel passage that produced it.

### 3.5 The Wish List

Grouped by type (creative decisions, historical research, character/location/costume/prop design, continuity, technical production), each item tagged `BLOCKER` or `NON-BLOCKER`, with: why it's needed, dependent scenes, partial evidence available, suggested answers, and approval status.

### 3.6 Additional field: Authorial Intent

Alongside factual evidence, tone/intent fields are tracked with the same rigor:

```json
{
  "field": "scene_tone_intent",
  "value": "claustrophobic, information withheld from audience",
  "status": "inferred",
  "confidence": 0.7,
  "source_passages": ["passage_11_04"]
}
```

This feeds directly into aesthetic-regime and directorial-style tagging (Section 6).

## 4. Subsystem B — Asset Construction Pipeline

**Core principle:** *Scenes request assets. They do not create assets directly.*

### 4.1 Pipeline

```
Approved Scene Breakdowns → Asset Requirement Aggregator →
Existing Asset Search → Reuse/Modify/Construct Decision →
Reference & Historical Validation → Asset Specification →
Construction Routing → Technical Validation → Artistic Approval →
Asset Library → Scene Assignment
```

### 4.2 Disposition Categories

```
EXACT_MATCH · VARIANT · DERIVATIVE · KITBASH · NEW_BUILD ·
PROCEDURAL · INSTANCE_ONLY · UNRESOLVED
```

### 4.3 Quality Tiers (applies to all asset classes)

```
HERO — close-up capable, full detail and animation
PRIMARY — repeated medium/wide shot use
SECONDARY — background, moderate detail
CROWD — simplified, variation-driven
DISTANT — silhouette/color only
MATTE — fixed/limited camera angles
PROXY — temporary layout placeholder
```

Quality level is determined by **what the camera sees and what the story requires**, not by an asset's historical importance.

### 4.4 Temporal Validity — Handling a 35-Year Story Span

Every asset variant carries a validity window, matched against a scene's story date, not just its identity:

```json
{
  "asset_id": "ENV-TAKAHASHIHOME-EXTERIOR",
  "variant_id": "ENV-TAKAHASHIHOME-EXTERIOR-V02",
  "valid_from": "1923-09-02",
  "valid_to": "1945-03-09",
  "change_reason": "rebuilt_post_earthquake"
}
```

A scene whose story date falls outside every existing variant's window auto-generates an `UNRESOLVED` requirement rather than silently reusing a wrong-era asset. Applies to environments, props, and vehicles the same way `effective_period` already applies to character state.

### 4.5 Validation Gate Statuses

```
DRAFT → REVIEW → CHANGES_REQUIRED → TECHNICALLY_APPROVED →
HISTORICALLY_APPROVED → ARTISTICALLY_APPROVED → PRODUCTION_APPROVED → DEPRECATED
```

Only `PRODUCTION_APPROVED` assets are assigned to final shots. An asset cannot advance past `TECHNICALLY_APPROVED` while `historical_reference_status` is `pending` or `unresolved` — hard gate, no exceptions, given the subject matter.

### 4.6 Dependency & Revision Handling

When a base asset (e.g., a shared skeleton) changes:

- **Automated compatibility check** — topology hash, bone count, UV layout comparison. Deterministic, no AI judgment.
- **Flagged for review** — anything failing the automated check gets `REVISION_REVIEW_REQUIRED`, ranked by number of downstream shots affected.

### 4.7 Naming Scheme

```
{TYPE}-{SUBTYPE}-{DESCRIPTOR}-{VARIANT}-{CONDITION}
```

| Type | Example |
|---|---|
| Character | `CHAR-REIA-AGE22` |
| Costume | `COST-JPN-KIMONO-FORMAL-WORN` |
| Prop | `PROP-WEAPON-RIFLE-ARISAKA-PRIMARY` |
| Environment | `ENV-KYOTO-TAKAHASHIHOME-KITCHEN` |
| Vehicle | `VEH-IJN-AKAGI-1942` |
| Effect | `FX-SMOKE-ARTILLERY` |

All-caps, hyphen-delimited. Condition/variant is always the last segment before version.

### 4.8 Construction Routing

- **LightWave** — hard-surface hero assets: vehicles, ships, aircraft, architecture, mechanical props.
- **DAZ Studio / Genesis** — character base meshes and rigs (see Section 5).
- **Blender** — rigging utilities, cloth/physics sim, geometry-nodes procedural generation, guide-pass rendering, compositing.
- **AI generation (local)** — routed by quality tier: Secondary/Crowd/Distant assets are AI-first with light human review; Hero/Primary assets are human-built or human-finished.

## 5. Subsystem C — Character & Performance Pipeline

### 5.1 The Character Object Model

Every character — named or crowd — inherits from a common schema:

```json
{
  "character_id": "CHAR-REIA",
  "species": "human",
  "gender": "female",
  "birth_date": "1920-XX-XX",
  "age_brackets": [
    { "bracket": "infant", "years": [0,3], "mesh_id": null, "voice_id": null },
    { "bracket": "child", "years": [3,12], "mesh_id": "MESH-REIA-CHILD", "voice_id": "VOICE-REIA-CHILD" },
    { "bracket": "teen", "years": [13,19], "mesh_id": "MESH-REIA-TEEN", "voice_id": "VOICE-REIA-TEEN" },
    { "bracket": "adult", "years": [20,35], "mesh_id": "MESH-REIA-ADULT", "voice_id": "VOICE-REIA-ADULT", "is_primary": true }
  ]
}
```

`is_primary` marks the bracket where the character spends the most story time — this is the **base build target** for mesh, rig, and voice. All other brackets are derived variants, not separate ground-up builds.

### 5.2 3D Base & Rigging — DAZ Studio / Genesis

- Genesis figures share one skeleton/rig across all body and age morphs — solves cross-age rig compatibility natively.
- Morph-dial system gives direct, deterministic creative control over mixed-heritage facial structure (relevant to Reia specifically), rather than relying on generative uncertainty.
- **Costumes are not sourced from the DAZ marketplace** — period wardrobe (1920s–40s Japan/China/US, military and civilian) does not exist there in meaningful depth. Costumes are built via LightWave/Blender and fitted onto the Genesis base.
- Because the 3D character exists purely as a motion/pose/rotoscope reference (never displayed on screen), DAZ render quality, shaders, and skin texture do not matter. What does matter: correct **volumetric bulk** (for depth-pass fidelity) and correct **seam/fold/button-level detail** (for lineart-pass fidelity) on costume geometry — texture-zero, geometry-adequate.
- **Pixar-style modular construction** (nude/base body + costume built and fitted separately) is retained and is specifically what makes clean LoRA training-image generation possible: render the bare rig for identity-LoRA training data, render costume-on-rig separately for costume-LoRA/reference data.

### 5.3 Motion Capture — Fully Local

- **BlendArMocap** — Blender addon, MediaPipe-driven, realtime or offline pose/hand/face tracking, drives rigs directly.
- **FreeMoCap** — webcam/phone-based, fully local processing, open source, research-grade.
- **EasyMocap** — research-grade multi-view toolbox, local.
- **Cascadeur** — local desktop app, strong free tier, used as the cleanup/physics layer after raw extraction (jitter removal, center-of-mass correction).
- **Adobe Mixamo** — one-time stock-motion library download + auto-rigging; lighter dependency than live cloud-processing services, acceptable for generic/background movement.
- Historical/archival combat footage may be used as a motion-extraction *reference* for large-scale chaotic action (crowd chaos, period-specific choreography), always retargeted first onto a neutral proxy "dummy" rig for cleanup before being applied to any named character.
- **Hard boundary:** motion capture sourced from pornographic footage is not used anywhere in this pipeline, for any scene, under any framing. Scenes depicting sexual violence (the Nanjing sequence) are handled entirely through directorial craft — camera restraint, framing choices, sound design, aftermath-as-payload — not through a motion-sourcing pipeline. This is a fixed line, not a per-scene judgment call.

### 5.4 Cloth Simulation

- Blender cloth physics / DAZ dForce, run **after** mocap is baked onto the rig (not simultaneously, to avoid simulation instability).
- Re-simulated per body when a costume is reused across meaningfully different body proportions (age variants) — weight-painted garments don't transfer cleanly across different volumes.

### 5.5 Style LoRA Architecture — Identity, Costume, and Regime Kept Separate

Three independent, stackable LoRA layers, composed at inference rather than trained together:

1. **Identity LoRA** — face, hair, body proportions only. Trained on neutral/bare-rig renders so costume is never baked into identity.
2. **Costume LoRA / IP-Adapter reference** — trained per costume *type*, reused across every character who wears it. Hero costumes (recurring, named-character, or carrying coded historical meaning — e.g., kimono crest/pattern) get a dedicated reference image and researched provenance. Background/crowd costumes use IP-Adapter reference only, no dedicated training.
3. **Regime style LoRA** — one per aesthetic regime (Section 6.2), reused across every character appearing in that regime.

A rendered shot stacks: identity + costume + regime. A costume change or new aesthetic regime does not require retraining the character.

**Dataset construction:** bootstrap style-training images by running cheap structural 3D renders through the base regime LoRA + ControlNet lock, then hand-curate the best 20–30 results into the actual training set — avoids hand-illustrating large datasets from scratch. Identity/costume/regime images are cleanly separable because of the modular (nude-base + costume-on-top) 3D construction in 5.2.

### 5.6 Voice Pipeline

- **Base voice model** built for each character's `is_primary` age bracket (own performance → RVC conversion via **MMVCServerSIO**).
- **Age-derived variants**: pitch+formant shift for adjacent brackets (works well for adult-to-adult decade gaps); for **child brackets specifically**, a supplementary real recording session with genuinely different vocal source material is budgeted, rather than attempting to synthetically stretch one adult base downward — known weak point of naive pitch-shift-only child voices ("40-year-old playing a 12-year-old" problem).
- **IndexTTS** — fully synthetic narration/background-line generation where a live performance isn't warranted.
- All three sourcing paths (performance+RVC / synthetic TTS / raw) tracked explicitly per dialogue line:

```json
{
  "voice_id": "VOICE-REIA-AGE22",
  "character_id": "CHAR-REIA",
  "source_type": "performance_rvc",
  "conversion_tool": "MMVCServerSIO",
  "model_path": "voices/reia_age22_v3.pth",
  "training_status": "approved"
}
```

- **Solo-performance technique**: scratch-track method (flat guide read of the scene partner's lines, played back for the performer to react to) or an IndexTTS-generated placeholder cue track — standard solo VO/ADR practice.
- Most VO is recorded at the same time as mocap for prominent scenes; crowd/incidental voice lines are produced independently via any of the three paths.

## 6. Subsystem D — Render & Style Pipeline

### 6.1 Guide Pass Generation (Blender)

Per shot, Blender renders:

- **Pose/skeleton pass** — from the mocap-driven rig.
- **Depth pass** — volumetric guide (costume bulk must be geometrically correct for this to read properly).
- **Lineart/edge pass** — via Freestyle; costume geometry must carry real seam/fold/button detail for this to have something to draw.
- **Flat-color / material-ID pass** — per-zone color guide (skin, hair, costume, accessories) so AI stylization has an unambiguous per-pixel color region, rather than relying on text-prompt color control alone.

"Animate on twos" (keys snapped to every 2 frames) applied before rendering to break the "too-smooth" 3D motion feel.

### 6.2 Six Aesthetic Regimes (art style — separate from directorial style, see 6.4)

| Regime | Visual target |
|---|---|
| Imperial Japan (1910–bombing) | Ghibli-paradigm: pastoral, soft diffuse light, painterly backgrounds |
| Pre-war China & US | Bluth-paradigm: gritty, dramatic lighting, lived-in imperfection |
| Battlefield / major historical events | Graphic-novel, high-grain, chaotic line work |
| China theater / occupation | "Vietnam war film" aesthetic: desaturated, muted, oppressive |
| War March — Winning (pre-war to Akagi's sinking) | Warm, golden, propaganda-epic grandeur |
| War March — Losing (Akagi to war's end) | Washed-out, exhausted, fraying-empire decay |

### 6.3 Character Base Style: Hybrid

- **Face/eye structure** — Studio Chizu-style geometric realism (clean planes, predictable topology, avoids the "goofy" American-cartoon trap on adult faces; also solves the 3D-puppeteering "orthographic trap" since sharp interlocking planes rotate correctly in 3D space).
- **Micro-expression/acting** — Bluth's Xanadu/NIMH-style sharp brow and mouth micro-movement, without elastic jaw distortion.
- **Hair, costume, body weight** — Bluth-style heavy anatomical physics: deep graphic shadow folds, thick moving hair shapes, not thin flat anime geometry.
- Real historical figures (Tojo, Hirohito, etc.) are exempted from expressive stylization entirely — rendered with stiffer, restrained, documentary-style animation and framing ("History Channel" treatment, Section 6.4), deliberately contrasting with the fictional cast.

### 6.4 Directorial Style Matrix (camera/lighting — independent of art style)

Tagged per scene in the production database, layered on top of the Section 6.2 art-style regime:

| Palette | Lens | Camera | Lighting |
|---|---|---|---|
| Patriotic ("War March – Winning") | Wide anamorphic, low angle | Heroic, deliberate | Hard directional, golden hour, lens flares |
| Combat / chaos ("post-Shanghai") | Standard/telephoto | Handheld shake, focus hunting | Flat overcast, desaturated |
| Historical figures ("documentary") | Neutral 35–50mm | Locked tripod, slow mechanical pans | Soft, diffused, vintage grain/B&W pass |
| Surreal aftermath | Any | Smooth floating/hyper-slow | Muted, disconnected, mutes environmental audio in edit |

```json
{
  "scene_id": "SC_12_SHANGHAI_STREETS",
  "aesthetic_regime": "CHINA_WAR_VIETNAM",
  "directing_palette": "COMBAT_HANDHELD",
  "camera_rig": { "lens_mm": 50, "handheld_shake_intensity": 0.8 },
  "lighting_preset": "overcast_muddy_gray"
}
```

### 6.5 ComfyUI Stylization

- ControlNet (lineart/depth/pose) locks 3D-driven motion and geometry.
- IP-Adapter supplies costume-pattern/crest reference where text prompts can't reliably convey specific graphic detail (e.g., kamon, seasonal motifs on formal kimono).
- Stacked LoRAs (identity + costume + regime) per Section 5.5.
- Prompts are **composed programmatically** from the shot's database record (`character_id` + `costume_id` + `color` + `regime`), never hand-typed per frame.
- Temporal consistency: per-frame ControlNet + IP-Adapter is favored over full motion-synthesis tools (e.g., AnimateDiff's motion module), since motion already comes from the locked 3D rig — the AI's job is repainting existing motion, not inventing new motion. Validate this choice empirically in the single-scene test rather than committing to one tool on paper, given how fast this space moves.

### 6.6 VFX

- Rain, dust, debris: Blender particle systems + a post-process sketch filter for hand-drawn streak conversion.
- Water/fluid: Mantaflow simulation, routed through a dedicated VFX lineart ControlNet to strip photorealism before compositing.
- Mud/wear-in-the-moment (e.g., Hiroshi's collapse): Blender Dynamic Paint, ground-as-brush / character-as-canvas.
- Large-scale destruction (blast waves, shockwaves): Force Fields (wind/turbulence) + Cell Fracture, timed via script rather than hand-keyed — with the caveat that where **no physical/eyewitness reference survives** (e.g., Saka's shockwave effects), the pipeline explicitly falls back to physics calculation + dramatic requirement, flagged as an intentional, rare exception rather than the default method.
- Procedural debris/crowd fields: Geometry Nodes scattering from a small kit of base assets (4–5 modeled debris shapes; 8–10 generic background character rigs recolored/varied via the AI style pass to read as a much larger population).

### 6.7 Lost/Destroyed City Reconstruction

```
Historical military maps/Gaihozu archives (verify per-city coverage before relying on them)
        ↓
BlenderGIS/blender-osm terrain (verify against pre-war topography for river-delta
        cities like Hiroshima, where land/coastline was postwar re-engineered)
        ↓
Buildify procedural building generation from a small modular kit
        ↓
ComfyUI regime style pass
```

Key sourcing leads: US Army Map Service city plans (Perry-Castañeda Library), Stanford's Gaihozu archive, Old Photos Japan (Kjeld Duits collection) — treated as strong leads requiring per-city verification, not confirmed solutions, tracked as wish-list items where coverage is uncertain.

## 7. Subsystem E — Compositing & Assembly

```
Styled shot passes → per-shot composite (Blender compositor / Natron) →
auto-populated Resolve timeline (scripted via Resolve's Python API,
pulling scene/shot order + duration from the production database) →
director pacing pass → color grade → scene/film output
```

- Per-shot composite templates are built once per aesthetic regime (matching the ComfyUI workflow structure) and reused.
- Editorial assembly starts from an auto-generated rough cut (Tier 2: AI-proposed pacing from scene metadata), with the human director retaining final authority over shot ordering, cut timing, and scene approval (Tier 3 — never automated).

## 8. Production Management Layer

### 8.1 Kitsu (CGWire)

Free, open-source, self-hosted (Docker). Serves as the **director's working dashboard**: asset/shot/task status, casting, dailies/playlist review. Mirrors IDs with the MongoDB production database (same asset/scene IDs in both systems) so Kitsu shows status at a glance while MongoDB remains the deep provenance/evidence store.

### 8.2 Automated vs. Manual Scene Modes

- `production_mode: automated | manual`, set at the scene review gate.
- **Automated mode** — scene's checklist items complete automatically and it flows directly into the render/style queue.
- **Manual mode** — checklist items require explicit human check-off in Kitsu before the scene advances.
- **Checklist templates are per scene type** (dialogue scene vs. battle scene vs. context/establishing scene), not one universal list — matches the quality-tier philosophy applied elsewhere.

### 8.3 Approval Gates (full list)

```
Novel ingestion approved → Timeline approved → Character bible approved →
Scene map approved → Screenplay scene approved → Breakdown approved →
Shot plan approved → Asset package approved → Animation approved →
Composite approved → Historical/sensitivity review (heaviest scenes only) →
Director final cut
```

### 8.4 Sensitivity/Context Review

Distinct from factual fact-checking: a human-judgment gate (ideally including outside readers, not solely the creator's own judgment) applied specifically to the heaviest historical material — Nanjing, the atomic bombings — verifying tone and impact land as intended, the same practice used on comparable historical dramatizations.

## 9. Data & Infrastructure

### 9.1 Database

- **MongoDB** — flexible schema for facts, characters, character states, scenes, assets, approvals, wish-list items — schema enforced at the application layer.
- Major collections: `projects, source_documents, source_passages, facts, characters, character_states, relationships, timeline_events, locations, assets, costumes, props, voice_assets, historical_sources, narrative_segments, screenplay_scenes, scene_breakdowns, shots, style_profiles, renders, approvals, issues, wish_list_items, construction_route_decisions`.

### 9.2 Version Control

**Perforce Helix Core**, self-hosted on the NAS. Free for up to 5 users/20 workspaces — comfortably covers solo use. Purpose-built for large binary files (no practical size limit), unlike Git/Git LFS. Covers .blend, .duf, LoRA, and texture file history/rollback.

### 9.3 Storage & Retention Policy

- Working storage: NAS with RAID (4×4TB + 8×2TB, ~32TB raw).
- Estimated render-layer footprint: ~3TB (accounts for redo/rejected work), plus asset library, LoRA models, mocap data, and reference archive on top.
- **Retention policy** (prevents unbounded growth): every file record carries `retention_class: scratch | archive`. Scratch (intermediate guide passes, rejected takes) auto-purged N days after a shot reaches `PRODUCTION_APPROVED`. Archive (final composites, approved 3D masters, trained LoRAs, the database itself) retained permanently.
- **Cold/long-term archive**: LTO tape + LTFS for everything tagged `archive`. Two copies of anything irreplaceable (on-site + offsite). Periodic test-restores required — an unverified tape backup is not a backup.

### 9.4 Batch Rendering

**Flamenco** (Blender Studio's open-source render farm manager) — manager/worker architecture for distributing headless Blender render jobs (`blender --background scene.blend --python render_script.py`) across the production server, with built-in queuing and retry. Extended to trigger the downstream ComfyUI stylization step as part of the same job chain where practical.

### 9.5 Hardware/GPU Allocation Policy

- **Production server**: dedicated to Flamenco render jobs + ComfyUI batch stylization inference.
- **Main workstation**: LoRA/RVC model training, VO recording/processing, general production work.
- This physical separation avoids GPU contention between training and rendering without requiring a software-level resource lock — stated here as an explicit operating policy.

### 9.6 Production Server Hardware Blueprint (Low-Budget Enterprise Build)

Minimum viable spec for the dedicated production server (Flamenco batch rendering + ComfyUI stylization inference, per the GPU allocation policy in 9.5). Pending validation in the single-scene test — flagged items below should be confirmed before final purchase.

**Core platform (refurbished enterprise workstation):**
- Chassis/motherboard: HP Z840 or Dell Precision T7910 (~$350–450 used) — robust multi-rail PSU and power delivery reused from enterprise-grade hardware.
- CPU: Dual Intel Xeon E5-2690 v4 (28C/56T, 2.6GHz base). *Caveat: this workload is GPU/VRAM-bound, not CPU-thread-bound — narrative-extraction LLM inference and ComfyUI stylization don't scale with these thread counts. The value here is chassis/PSU/RAM-channel capacity at a low price point, not raw CPU throughput.*
- RAM: 128GB DDR4 ECC Registered, quad-channel — headroom for Blender geometry-node caches, local MongoDB/Kitsu containers, and large asset memory maps running concurrently.

**GPU / AI inference:**
- Specified: RTX 3060 (12GB) or RTX 2080 Ti (11GB). *Caveat — flagged for reconsideration: this server runs unattended overnight batches stacking SDXL + ControlNet + IP-Adapter + multiple chained LoRAs per shot. 11–12GB is workable but leaves little margin; an OOM crash mid-batch with nobody present to restart it is a real risk at this VRAM level. A used RTX 3090 (24GB) is worth the price difference specifically because this machine must run unattended — validate actual VRAM headroom in the single-scene test before finalizing either way.*

**Storage:**
- OS/system: 1TB NVMe via PCIe x4 adapter card (bypasses older motherboard bootable-M.2 limitations on this generation of board).
- Scratch/cache: 2TB enterprise SATA SSD or secondary NVMe for active frame-buffer scratch during guide-pass renders and local Perforce workspace caching. *Caveat: this is smaller than the ~3TB estimated render-layer footprint (Section 9.3) — size up or rely on disciplined retention-policy purging to avoid filling mid-production.*

**Software/network:**
- OS: Ubuntu LTS, matching the Docker/Kitsu containerization target.
- Local Perforce workspace client linked to the NAS repository; local MongoDB and Kitsu daemon instances.
- Network: onboard Gigabit LAN minimum; a used 10GbE PCIe card is worth the modest cost given the multi-terabyte asset/render transfer volumes already estimated for this project.

### 9.6.1 Recommended Specification Tier

A step up from the minimum blueprint above, aimed at removing the contention/headroom risks flagged as caveats — not a different design, the same architecture with more margin.

**Chassis/motherboard:** HP Z8 G4 or Dell Precision 7920 in place of the Z840/T7910 — same reused-enterprise-workstation value, but native PCIe4 M.2 NVMe boot support, removing the boot-workaround entirely and giving real NVMe bandwidth for scratch I/O.

**CPU:** No upgrade recommended here — thread count is not the bottleneck for this workload (see caveat above); budget goes to GPU/storage instead.

**GPU — dual-card configuration recommended over a single larger card:**
- Primary: used RTX 3090 (24GB) — runs ComfyUI's stacked SDXL + ControlNet + IP-Adapter + chained LoRA inference with real headroom.
- Secondary: used RTX 3060 (12GB) — dedicated to Flamenco's Blender guide-pass rendering (lineart/depth/flat-color passes are lightweight relative to full path-traced rendering, so this card doesn't need to be powerful).
- Rationale: running both workloads concurrently on one card serializes them overnight; two cards let Flamenco and ComfyUI batches run in true parallel, and provide failure redundancy if one card has an issue mid-batch.

**RAM:** 256GB DDR4 ECC — real headroom against two GPUs' driver overhead plus concurrent MongoDB/Kitsu/Blender/ComfyUI processes, versus the tighter margin at the minimum tier's 128GB.

**Storage — multiple 4TB+ scratch drives, not one larger drive:**
- Two or more 4TB+ PCIe4 NVMe drives, one assigned per concurrent job stream (e.g., one for Blender/Flamenco render output, one for ComfyUI stylization output) — avoids both pipelines contending for the same disk I/O queue during simultaneous batches.
- Since this is regenerable scratch data (not archive), striping across drives (RAID0) is reasonable here for raw throughput — unlike the NAS archive tier, which needs redundancy, not speed.
- Check sustained-write/TBW endurance rating specifically — this drive sees continuous heavy write cycles under batch production, not typical desktop usage patterns.

**Network:** 10GbE treated as standard at this tier, not optional — at recommended-tier throughput (dual GPU, multiple scratch drives), Gigabit becomes the actual bottleneck moving finished sequences to the NAS.

### 9.7 Audio/Score

Original score and sound design outsourced (e.g., contracted composer) rather than built in-house. Tracked via a lightweight `audio_assets` collection (composer, license terms, delivery format, associated scene/cue) for the same provenance discipline applied elsewhere.
